# HELIX 홈페이지 코드 안정화 목표 수준 및 최종 종료 기준서

- **문서 버전:** v2.0
- **기준일:** 2026-11-24 KST
- **목표 수준:** Level 4 — 실무적·구조적 안정성
- **적용 범위:** HELIX 공식 홈페이지의 제작, 수정, 확장, 배포 및 유지보수

## 01. 작업 목적

본 안정화 작업의 목적은 기술적으로 완벽한 코드나 무결점 시스템을 만드는 것이 아니다.

HELIX 공식 홈페이지의 지속적인 제작·수정·확장·배포 및 유지보수 과정에서 예측 가능한 안정성을 확보하고, 변경에 따른 오류 발생 가능성과 장애 영향 범위를 실질적으로 줄이는 것이 목적이다.

목표 수준은 일반적인 홈페이지의 기본적인 작동 안정성을 넘어서는 높은 수준의 실무적·구조적 안정성으로 설정한다.

단, 고신뢰 인프라, 대규모 서비스 플랫폼 또는 미션 크리티컬 시스템에 요구되는 수준의 과도한 설계와 검증은 지양한다.

**홈페이지 제작을 지원하는 안정적인 기반을 마련하는 것이 목적이며, 안정화 자체를 독립적인 소프트웨어 개발 프로젝트로 확대하지 않는다.**

## 02. 목표 안정화 수준

다음 5단계는 본 프로젝트를 위한 자체 평가 기준이다.

| 단계 | 정의 |
|---|---|
| Level 1 | 작동 안정성 |
| Level 2 | 기본적인 오류 방어 및 예외 처리 |
| Level 3 | 실사용 및 운영 안정성 |
| **Level 4** | **변경·확장·유지보수에 대응하는 구조적 안정성** |
| Level 5 | 극단적인 장애와 복합적 예외까지 대응하는 고신뢰 시스템 |

본 프로젝트의 목표는 **Level 4의 충분한 달성**이다.

Level 5에 해당하는 기술적 고도화는 별도의 필요성이 입증되지 않는 한 수행하지 않는다.

최소한으로 작동하는 상태에서 타협하지 않되, 기술적 완벽성을 위해 작업 범위를 확장하지 않는다.

## 03. 안정화 단계별 목표

### 3-1. 1차 — 핵심 구조 안정화

서로 얽혀 영향을 주던 코드와 연결 관계를 정리하고, 주요 기능에서 오류가 연쇄적으로 발생하는 구조를 개선한다.

주요 범위:
- 주요 CSS·JS 중복 및 충돌 개선
- 핵심 기능 간 불필요한 의존성 제거
- 실행 순서 및 초기화 문제 개선
- 주요 자산의 버전 혼용 방지
- 메뉴·예약창·Hero·스크롤 등 주요 기능 안정화
- 실제 운영 반영 및 핵심 기능 검증

### 3-2. 2차 — 구조 체계화 및 AI 작업 방식 안정화

1차에서 정리한 핵심 구조를 기준으로 전체 홈페이지의 코드 관리 방식과 향후 수정 절차를 체계화한다.

주요 범위:
- 기능별 코드 묶음 분류 및 역할·소유권 정립
- 공통 코드와 페이지별 코드의 관리 기준 통일
- 공유 CSS·JS와 로더의 영향 범위 정리
- 잔여 결합 및 불필요한 기능 간 간섭 개선
- 대표적인 페이지 추가·수정 작업에 대한 회귀 검증
- 기존 자동 검사 도구의 보완 및 재사용
- AI 코드 수정 과정에 필수 작업 수칙과 검증 절차 적용
- 배포 및 복구 기준 표준화
- 실무용 기술 지침 및 인계 자료 정리

**2차의 핵심은 코드를 정돈하는 것뿐 아니라, 향후 AI가 코드를 수정해도 구조가 다시 쉽게 얽히지 않도록 작업 방식 자체를 개선하는 것이다.**

## 04. 영역별 필수 달성 기준

### 4-1. 코드 독립성 및 영향 범위 통제

- 개별 기능의 수정이 무관한 기능의 오류로 이어지는 구조적 문제를 해소한다.
- 공통 코드와 개별 코드의 역할 및 책임 범위를 명확히 구분한다.
- 공유 자산 및 의존 관계에 따른 변경 영향 범위를 예측할 수 있어야 한다.
- 의도된 공통 변경을 제외하고 불필요한 기능 간 간섭을 방지한다.

단, 모든 코드를 완전히 독립된 모듈로 분리하거나 기존 구조를 전면 재설계할 필요는 없다.

### 4-2. 회귀 오류 방지

- 기존에 발견하고 해결한 오류에 대한 재발 방지 체계를 확보한다.
- 코드 수정, 콘텐츠 변경, 페이지 추가, 공통 요소 변경 등 대표적인 작업 유형에 대한 회귀 검증을 수행한다.
- 수정 전후의 기능 및 화면 상태를 비교할 수 있어야 한다.
- 새로운 수정으로 기존 정상 기능이 손상되지 않았음을 확인한다.

단, 가능한 모든 수정 조합과 작업 순서를 전수 검증하지 않는다.

### 4-3. 코드 실행 및 생명주기 안정성

다음과 같이 실제 웹 운영에서 발생 가능성이 높은 문제를 통제한다.

- 스크립트 실행 순서
- 초기화 누락 및 중복 초기화
- 중복 실행 및 이벤트 중복 등록
- 비동기 처리 및 타이밍 충돌
- 지연 로딩 및 동적 콘텐츠 처리
- 페이지 전환과 재진입
- 초기 렌더링 및 첫 화면 표시
- 일반적인 JavaScript 실행 예외

각 문제에 대한 방어는 실제 구조와 발생 가능성에 근거해야 한다.

### 4-4. 장애 격리 및 복구

- 개별 기능의 오류가 홈페이지 전체의 작동 중단으로 확산되지 않도록 한다.
- 비핵심 기능이 실패하더라도 핵심 콘텐츠와 주요 사용자 동선은 유지한다.
- 일시적 오류에 대한 자동 복구는 효과적이고 안전한 범위에서 적용한다.
- 자동 복구가 불가능한 오류는 안전한 중단, 대체 동작 또는 수동 복구가 가능해야 한다.
- 오류의 발생 위치와 원인을 파악할 수 있어야 한다.
- 복구 과정에서 중복 실행, 무한 재시도 또는 새로운 오류가 발생하지 않도록 한다.

모든 장애의 자동 복구는 요구하지 않는다. 영구적인 장애를 무리하게 자동 복구하려는 구조보다 안전한 실패 처리를 우선한다.

### 4-5. 자산 및 버전 관리

- 신구 버전의 의도하지 않은 혼용 방지
- 중복 자산 로딩 및 실행 방지
- 공통 자산의 책임 및 소유권 명확화
- CDN 및 캐시로 인한 주요 버전 충돌 방지
- 주요 자산의 로딩 실패 및 지연 대응
- 정상 버전 식별 및 복구 가능성 확보

실제 운영 환경의 자산과 배포 구조를 기준으로 검증한다.

### 4-6. 실사용 환경 호환성

- 주요 데스크톱 및 모바일 브라우저
- Chrome, Safari, Edge 및 주요 모바일 환경
- 대표적인 화면 크기와 반응형 경계
- 일반적인 네트워크 지연 및 일시적 자산 로딩 실패
- 새로고침, 재접속, 페이지 이동 등 일반적인 사용자 행동

홈페이지의 실제 방문 환경을 중심으로 검증한다.

모든 브라우저 버전, 구형 기기, 극단적인 네트워크 조건에 대한 완전한 호환성은 요구하지 않는다.

실제 iOS Safari 실기기 검증과 WebKit 자동 검증은 서로 다른 증거로 구분한다. 실기기 접근이 불가능하면 미검증 범위와 위험을 기록하고 조건부 허용 여부를 판단한다.

### 4-7. 확장성 및 유지보수성

다음 작업을 기존 시스템의 대규모 재설계 없이 수행할 수 있어야 한다.

- 신규 진료과 페이지 추가
- 지점별 페이지 및 콘텐츠 확장
- 기존 콘텐츠 수정 및 삭제
- 공통 UI 및 컴포넌트 변경
- 신규 기능 및 스크립트 추가
- 이미지 및 기타 자산 교체
- 반응형 디자인 수정

향후 실제로 예정된 제작 및 운영 업무를 기준으로 판단한다.

아직 정의되지 않은 미래 요구사항을 가정하여 범용 시스템을 구축하지 않는다.

### 4-8. 배포 및 원복 안정성

- 정상 작동이 확인된 기준 버전을 확보한다.
- 변경 사항과 적용 범위를 식별할 수 있어야 한다.
- 배포 전후 핵심 기능 검증이 가능해야 한다.
- 배포 실패 또는 주요 오류 발생 시 안전하게 원복할 수 있어야 한다.
- 백업 및 원복 절차의 실효성을 확인한다.

복잡한 배포 인프라 구축보다 현재 운영 환경에서 신뢰할 수 있는 절차를 확보하는 것을 우선한다.

**매번 과거 Webflow 사이트 전체의 완전한 복원을 입증할 필요는 없다.** 실제 변경되는 영역에 대해 실효성 있는 복구 수단을 확보하고, 코드 설정·디자인·CMS·폼 등 복구 범위를 구분한다.

변경 범위를 확인할 수 없거나 중대한 변경을 복구할 수 없는 경우에는 해당 게시를 보류한다.

### 4-9. 검증 재현성

- 기존 오류에 대한 회귀 검증을 반복 수행할 수 있어야 한다.
- 정상, 오류, 복구, 안전한 실패 상태를 구분하여 판정한다.
- 실제 운영 자산을 기반으로 대표적인 조건을 검증한다.
- 검증 결과는 다른 작업자 또는 독립적인 검토자가 재확인할 수 있어야 한다.
- 테스트 통과와 미검증 상태를 명확히 구분한다.

기존 검증 체계가 충분하다면 이를 활용한다. 검증 시스템 자체를 별도의 개발 프로젝트로 고도화하지 않는다.

### 4-10. 문서화 및 작업 인계

다음 내용을 실무적으로 활용 가능한 수준으로 기록한다.

- 주요 코드 구조와 역할
- 공통 자산 및 의존 관계
- 주요 수정 시 주의사항
- 기능 추가 및 확장 방법
- 검증 실행 방법
- 오류 확인 및 복구 방법
- 배포 및 원복 절차
- 잔여 위험과 유지보수 과제

문서의 분량이나 형식적 완성도보다 실제 활용성을 우선한다.

## 05. AI 작업 수칙 및 수정 프로세스

본 항목은 2차 안정화의 필수 달성 기준이다.

홈페이지 코드가 정돈되어 있더라도 AI가 개별 작업만 고려해 수정하면 구조가 다시 복잡해질 수 있다.

따라서 AI의 판단 능력에만 의존하지 않고, 저장소의 필수 작업 지침과 자동 검사를 결합한다.

### 5-1. 필수 작업 지침

기존 AGENTS.md를 AI 작업 수칙의 기본 진입점으로 사용한다.

CLAUDE.md와 기존 기술 자료는 관련 제약·기술 이력·재발 방지 사례의 참고자료로 사용한다.

오래된 기록과 현재 코드가 충돌하면 실제 저장소 및 운영 상태를 확인하고 최신 기준으로 정리한다.

동일한 규칙을 여러 문서에 중복 정의하지 않는다.

Work·Codex 등 작업 환경이 달라도 같은 기준을 적용한다.

모든 AI 도구가 지침 파일을 자동으로 읽는다고 가정하지 않는다. 각 환경의 작업 시작 절차에서 지침을 실제로 확인하도록 한다.

### 5-2. AI의 수정 전 필수 확인

AI는 코드를 수정하기 전에 다음을 확인한다.

1. 작업 목적과 정확한 수정 범위
2. 해당 코드의 역할과 소유권
3. 연결된 페이지·공통 코드·관련 기능
4. 기존 정상 동작 및 보존해야 할 조건
5. 예상되는 회귀 위험과 영향 범위
6. 필요한 검사와 복구 방법

요청받은 부분만 보는 국소적인 수정이 아니라, 실제 영향 범위를 고려한 최소 수정을 원칙으로 한다.

다만 모든 작업에서 홈페이지 전체를 처음부터 분석하지 않는다.

### 5-3. AI의 수정 중 필수 수칙

- 기존 정상 코드 최대한 보존
- 최소 충분 범위에서 수정
- 무관한 코드의 임의 정리 금지
- 불필요한 파일 분할·통합·이름 변경 금지
- 검증되지 않은 자산 버전 혼용 금지
- 공통 코드 변경 시 영향받는 페이지 확인
- 정상 기능과 기존 디자인 보존
- 다른 AI 작업과 파일 수정 충돌 방지
- 비공개 자료와 운영 데이터 보호

새로운 개선점이 발견되어도 현재 작업에 필수적이지 않다면 임의로 수정하지 않는다.

### 5-4. AI의 수정 후 필수 검증

다음 절차를 기본으로 한다.

**수정 → 자동 검사 → 영향받는 기능 회귀검증 → 오류 시 수정·재검사 → 배포 전 검증 → 결과 기록**

검사 실패 시 원인을 확인하고 수정한다.

검증되지 않은 작업을 완료했다고 보고하지 않는다.

코드 수정, 자동 검사, 스테이징 적용, 실제 브라우저 확인, 운영 반영 상태를 구분한다.

각 작업의 규모와 위험에 맞춰 필요한 검사만 수행한다.

### 5-5. 자동 검사 도구 적용

기존 홈페이지 GitHub 저장소의 검사 스크립트와 GitHub Actions를 활용한다.

필요한 경우 다음 검사를 보완한다.

- 코드 문법 및 실행 오류
- 공통·페이지 코드 연결 및 버전 일치
- 대표적인 메뉴·예약창·Hero 동작
- 기존 회귀 오류 재발
- 주요 반응형 화면
- 변경된 기능의 실제 동작
- 배포 자산의 무결성

AI가 코드를 수정할 때 적절한 검사 도구를 실행하도록 작업 절차를 정한다.

검사 실패 시 배포를 보류한다.

자동 검사 도구가 모든 오류를 발견한다고 가정하지 않는다.

GitHub 검사와 Webflow Publish가 기술적으로 연결되지 않은 경우에는 수동 승인 절차로 통제하며, 자동 차단이 구현됐다고 표시하지 않는다.

### 5-6. AI 작업 완료 기준

AI의 작업 완료는 단순한 코드 작성이 아니다.

- 요청한 변경이 구현되었는가?
- 기존 주요 기능이 유지되는가?
- 예상 영향 범위를 검사했는가?
- 오류 발생 시 원인과 복구 방법을 파악할 수 있는가?
- 실제 적용 여부를 확인했는가?
- 다음 작업자가 결과를 활용할 수 있는가?

이를 충족하는 수준에서 작업을 종료한다.

## 06. 오류 등급 및 처리 원칙

| 등급 | 정의 | 처리 기준 |
|---|---|---|
| P0 | 전체 장애·데이터 손실·심각한 보안 문제 | 미해결 0건 |
| P1 | 핵심 기능 장애·주요 사용자 동선 손상·심각한 회귀 | 미해결 0건 |
| P2 | 제한적인 기능 오류·일반적인 안정성 문제 | 해결 또는 위험 통제 |
| P3 | 경미한 시각적 차이·최적화·편의 개선 | 기록 후 이관 가능 |

P2는 발생 가능성, 영향도, 재발 가능성, 복구 가능성을 종합해 판단한다.

개별적으로 경미해도 반복되거나 누적되어 운영에 지장을 주는 문제는 해결 대상에 포함한다.

개인정보 및 예약 데이터의 정확성에 영향을 주는 문제는 실제 피해 확인 여부와 별개로 위험도를 평가한다.

P0·P1으로 분류된 문제는 단순 후속 과제로 이관하지 않는다.

## 07. 적정 안정화와 과잉 엔지니어링의 경계

| 적정 안정화 | 과잉 엔지니어링 |
|---|---|
| 현실적인 오류 발생 조건 방어 | 이론적으로 가능한 모든 오류 방어 |
| 주요 기능 및 코드의 책임 분리 | 모든 요소의 완전한 독립화 |
| 대표적인 변경 유형 검증 | 모든 변경 조합 전수 검증 |
| 주요 장애의 안전한 복구 | 모든 장애의 자동 복구 |
| 실제 운영 환경 대응 | 극단적이고 희귀한 환경까지 대응 |
| 예정된 콘텐츠 및 기능 확장 지원 | 미정의 미래 요구까지 선제 대응 |
| 유지보수 목적의 구조 개선 | 기술적 이상을 위한 전면 재설계 |
| 반복 가능한 검증 체계 확보 | 검증 체계 자체의 무한 고도화 |
| 실무에 필요한 문서화 | 형식적 완전성을 위한 과도한 문서화 |

새로운 작업을 추가하기 전 반드시 다음 사항을 판단한다.

1. 실제로 발생했거나 합리적으로 예상할 수 있는 문제인가?
2. 홈페이지의 제작·운영·유지보수에 실질적인 영향을 주는가?
3. 기존 방어 체계로 충분히 통제할 수 없는가?
4. 해결에 필요한 공수 대비 얻을 수 있는 안정성 향상이 충분한가?

위 질문에 대한 근거가 부족하다면 신규 작업으로 추가하지 않는다.

## 08. 작업 범위 통제 원칙

- 기존에 검증을 통과한 정상 코드와 기능은 최대한 보존한다.
- 수정이 필요한 영역만 최소 충분 범위에서 개선한다.
- 새로운 위험의 발견과 새로운 작업의 착수를 동일시하지 않는다.
- 동일한 문제를 명칭만 변경하여 반복적으로 해결하지 않는다.
- 새로운 기술적 가능성의 발견을 기존 종료 기준의 상향 근거로 사용하지 않는다.
- 기존 검증 결과가 유효하다면 불필요하게 처음부터 재검증하지 않는다.
- 수정된 부분과 실제 영향 범위를 중심으로 재검증하되, 최종적으로 핵심 회귀 검증을 수행한다.
- 검증 과정에서 발견된 개선 가능성을 모두 필수 해결 과제로 전환하지 않는다.

**본 기준서는 안정화의 목표인 동시에 작업 범위의 상한선이다.**

## 09. 기존 작업 재평가

본 기준서를 적용하기 위해 기존 작업을 무조건 처음부터 다시 수행하지 않는다.

현재까지 확보한 소스, 수정 내역, 검증 결과, 감사 결과 및 잔여 과제를 본 기준에 대조하여 다음과 같이 재분류한다.

| 판정 | 의미 |
|---|---|
| 충족 | 기존 증거로 충분히 입증된 항목 |
| 필수 보완 | 목표 수준에 도달하기 위해 필요한 항목 |
| 조건부 허용 | 위험이 제한적이고 통제 가능한 항목 |
| 미검증 | 증거가 부족하거나 환경상 확인하지 못한 항목 |
| 범위 초과 | 목표 수준을 넘어서는 과잉 안정화 항목 |

기존 과제라는 이유만으로 반드시 완료해야 한다고 판단하지 않는다.

반대로 기존에 완료 처리되었다는 이유만으로 증거가 부족한 항목을 통과시키지 않는다.

범위 초과로 판정한 항목은 추가 수행하지 않는다.

## 10. 공수 및 잔여 작업 관리

현재까지 약 10작업일의 추가 안정화 공수가 투입된 상황을 고려한다.

작업 착수 전 다음 내용을 산정한다.

- 현재 목표 수준 대비 달성 상태
- 실제로 남아 있는 필수 보완 작업
- 각 작업의 필요성과 예상 공수
- 필수 작업 간 선후 관계
- 안정화 완료까지의 예상 잔여 공수

추가 작업 중 새로운 문제가 발견되더라도 본 기준서를 충족하는 데 필요한 경우에만 작업에 포함한다.

기존 예상 공수를 초과할 가능성이 발생하면 무조건 작업을 연장하지 않고 원인, 필요성 및 대안을 명시한다.

## 11. 최종 종료 승인 기준

다음 조건을 모두 확인한다.

- [ ] 알려진 P0 및 P1 오류가 모두 해결되었다.
- [ ] 주요 P2 오류가 해결되었거나 안전하게 통제된다.
- [ ] 기존에 발견된 주요 회귀 오류에 대한 재발 방지가 검증되었다.
- [ ] 실제 운영 자산을 기준으로 핵심 기능의 정상 작동이 확인되었다.
- [ ] 대표적인 코드 및 콘텐츠 변경에도 기존 기능이 유지된다.
- [ ] 주요 실행 순서, 초기화, 비동기 처리 및 버전 충돌 문제가 통제된다.
- [ ] 현실적인 장애 상황에서 영향 범위가 제한되고 안전한 복구 또는 실패 처리가 가능하다.
- [ ] 주요 PC·모바일 환경에서 정상 작동이 확인되었다.
- [ ] 예정된 홈페이지 제작 및 확장 작업을 수행할 수 있다.
- [ ] 정상 버전의 백업과 변경 범위에 적합한 원복 절차가 검증되었다.
- [ ] 향후 동일한 안정성을 재검증할 수 있다.
- [ ] AI 작업 수칙이 실제 저장소에 반영되고 작업 절차에 적용된다.
- [ ] 주요 AI 작업에서 수정 전 영향 분석과 수정 후 검증이 수행되는 것을 확인했다.
- [ ] 실무에 필요한 유지보수 및 작업 인계 자료가 확보되었다.
- [ ] 잔여 위험과 개선사항이 분류되었다.
- [ ] 최종 수정본을 기준으로 핵심 회귀 검증을 통과하였다.

검증하지 못한 항목을 통과로 간주하지 않는다.

환경 또는 자산의 제약으로 검증할 수 없는 항목은 별도로 명시하고, 실제 운영 위험에 따라 종료 가능 여부를 판단한다.

## 12. 최종 보고 및 종료 판정

최종 보고에는 다음 내용을 포함한다.

1. 목표 안정화 수준 달성 여부
2. 영역별 충족 상태 및 근거
3. 해결한 구조적 문제
4. 실제 검증 결과
5. 검증 한계 및 미검증 항목
6. 허용 가능한 잔여 위험
7. 유지보수 이관 과제
8. 범위 초과로 제외한 과제
9. AI 작업 수칙 및 검증 절차 적용 상태
10. 홈페이지 본 제작 공정 복귀 가능 여부

최종 판정은 다음 중 하나로 명확히 제시한다.

- **안정화 완료:** 목표 기준 충족, 본 제작 복귀 가능
- **조건부 안정화 완료:** 주요 기준 충족, 제한적인 위험을 관리하면서 본 제작 복귀 가능
- **필수 안정화 미완료:** P0·P1 또는 필수 구조적 위험이 남아 보완 필요

## 13. 최상위 판단 원칙

높은 완성도는 추구하되 기술적 완벽성을 추구하지 않는다.

정상 작동하는 것만으로 만족하지 않는다. 그러나 모든 가능성을 통제하려 하지도 않는다.

실제 운영에서 반복적인 수정과 확장이 가능하고, 변경 영향 범위를 예측할 수 있으며, 오류가 발생하더라도 이를 통제하고 복구할 수 있는 충분히 견고한 상태를 목표로 한다.

AI의 판단에만 의존하지 않고 명확한 작업 규칙과 재현 가능한 검사로 수정 결과를 관리한다.

추가적인 기술적 개선이 홈페이지의 실질적인 안정성 향상보다 코드 자체의 이상적인 완성도를 높이는 데 기여하기 시작하는 지점을 종료 경계로 삼는다.

**안정화는 홈페이지 제작을 지원하기 위한 공정이지, 독립적인 소프트웨어 안정화 솔루션 개발 프로젝트가 아니다.**

본 기준을 충족하면 안정화 작업을 종료하고 HELIX 홈페이지 본 제작 공정으로 복귀한다.
